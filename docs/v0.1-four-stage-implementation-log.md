# Agent Memory Utility v0.1：四阶段实施日志

- 状态：已完成并冻结
- 实施与整理时间：2026-09-05 至 2026-09-12
- 版本范围：`v0.1.0` 及其发布后文档整理

## 文档定位

本文由早期的《四阶段任务安排与交付目标》反向整理而成。原文件是 v0.1 的前置计划；本文记录最终实际完成的工作、验证证据、与原计划的偏差，以及它们如何共同导向 v0.2。

v0.1 并不声称完整复现 UltraRAG、MiniCPM-Embedding、RAG-DDR 或 VisRAG。四项工作分别承担系统、检索、效用和多模态表示的技术支点，最终形成同一个研究原型：

> 从可靠持久化出发，测量记忆增长时的检索表现，再区分“检索到”与“真正被利用”，并用轻量案例检查纯文本表示的边界。

## 最终研究问题与实施概览

## Stage 1 日志：Persistent Memory 与 UltraRAG 接入

### 原计划

实现一个最小持久化记忆库，支持写入、读取、检索、进程重启恢复和索引重建；通过 MCP 接入 UltraRAG，形成 `retrieve → reason → answer → memory write` 闭环。

### 实际完成

- 建立 `src/longmem` Python package、配置、测试、脚本和集成目录。
- 采用 JSONL 作为权威事件日志、SQLite 作为可恢复状态投影、FAISS CPU 作为可重建向量索引。
- 实现 `write`、`get`、`search`、`list` 和 `rebuild_index` 的 Python API 与 CLI。
- 使用稳定 `memory_id`、`supersedes_id` 和 `embedding_version` 管理事实替代与索引版本。
- 处理日志先提交后的恢复、未完成尾部、坏行拒绝、SQLite/FAISS 丢失或损坏、线程及进程并发等情况。
- 建立独立 stdio MCP 服务，提供 `memory_write`、`memory_search`、`memory_get`、prompt construction、generator 和 response write-back。
- 通过 UltraRAG 官方 console CLI 完成 build/run，并验证跨进程写入、重启后检索和第三进程复查。
- 提供确定性 test backend 与真实本地模型两种 demo 路径。

### 验证结果

- 最终仓库测试总计 42 项通过；Stage 1 验收时的 20 项核心测试覆盖存储、恢复、并发和索引版本路径。
- test 与 model 两种端到端 demo 均通过。
- 真实模型最小案例中，系统正确检索 Alice 的编辑器事实并生成 `Neovim`。
- evidence IDs 写入审计元数据；它们记录提供给生成器的证据，不被解释为模型内部利用证明。

### 与原计划的偏差

- 原计划只要求三个 memory MCP 接口，实际还完成 prompt、generation 和 response write-back 的完整编排接口。
- 原计划中的“视频文件”没有作为发布物保存；最终保留可执行 demo 与录屏脚本，避免将二进制展示材料纳入仓库。
- 未在第二台全新机器复验安装流程；AMD/ROCm 本机范围与兼容修改另有部署报告记录。

## Stage 2 日志：Memory Budget 与检索增长实验

### 原计划

使用 MiniCPM-Embedding 测量 100 至 10,000 条记忆下的 Recall、MRR、延迟、索引大小与检索 token，并比较 full、recency、importance 和 semantic deduplication。

### 实际完成

- 构造带 `target_memory_id` 与 `target_canonical_id` 的英文合成事实、时间更新、重复项和干扰项。
- 使用 `event_order` 表示合成事件顺序，避免与真实写入时间混用。
- 将开发主题与测试主题分离；semantic deduplication 阈值只用 seed 77 的开发查询校准，并冻结于 `frozen-v0.1.json`。
- 运行 5 个规模、2 种目标时间场景、3 个随机种子，以及匹配预算下的 4 种策略。
- 保存逐查询预测、聚合表、源文件 hash、manifest、三张图和可重复验证记录。

### 验证结果

- 共 300 个唯一运行，覆盖、固定预算、主题隔离、召回重算、目标保留分母和指标边界均通过验证。
- balanced 场景全量保留在 10,000 条记忆时 Recall@5 为 `0.949`。
- 同一规模的 50% 保留预算下，importance、recency 和 semantic deduplication 的 Recall@5 分别为 `0.486`、`0.537` 和 `0.519`。
- old 场景显示 recency 的结构性风险：当目标事实偏旧时，10,000 条、50% 预算下 Recall@5 为 `0.000`。
- 全量 10,000 条索引约 `87.89 MiB`；50% 预算约 `43.95 MiB`。

### 与原计划的偏差

- 结果没有支持“语义去重一定最好”之类的预设结论；策略表现明显依赖目标事实的时间分布。
- 延迟被拆成查询编码和 FAISS 搜索分项，不把模型加载、日志重放、持久化或 MCP 算入完整服务延迟。
- importance 是随机合成元数据基线，不等同于人工标注或学习得到的重要度。
- 最终 runner 统一为 `benchmark.py`、`analyze.py` 和 `report.py`，内部迭代名不再作为发布接口。

## Stage 3 日志：Memory Utility 与检索—利用差距

### 原计划

借鉴 RAG-DDR 的问题意识，比较 no-memory、relevant、irrelevant、conflicting 和 consolidated 条件，分别记录检索命中与回答得分，避免完整复现其训练流程。

### 实际完成

- 将 Stage 2 的事实与真实 top-k 检索结果转成 54 个生成任务。
- 运行 11 个条件，包括五类人工控制条件，以及 full/semantic-dedup 在 `k=1/3/5` 下的真实检索回放。
- 主实验生成 594 个配对回答，并保存 prompt、回答、证据 ID、EM、F1、recall 与 token 数。
- 增加 6 个开发样例、54 个测试样例的输出协议控制；正式测试生成 648 个回答。
- 将内容条件统一为明确命名，例如 `consolidation_keep_temporal_cue` 和 `consolidation_strip_temporal_cue`。
- 增加 hit-but-wrong、retrieval miss、positive utility 和 consolidation degradation 的诊断案例。

### 验证结果

- full memory、`k=3` 的 Recall 为 `1.000`，但 exact match 为 `0.889`，54 个样例中有 6 个 hit-but-wrong。
- full memory、`k=5` 的 exact match 上升到 `0.944`，同时平均记忆上下文增至约 68 tokens。
- relevant 条件 exact match 为 `1.000`；no-memory 为 `0.000`。
- 去除时间提示的 consolidation 条件原始 exact match 为 `0.352`；事后首行截取诊断为 `0.704`，表明输出协议和措辞会显著影响测量。
- 控制实验通过开发集协议选择、配对覆盖、无重复回答、答案抽取和得分重算等验证。

### 与原计划的偏差

- 原设想中的简单五条件实验扩展为五类人工控制加六类检索回放条件。
- “命中但答错”只能作为行为诊断，不能证明模型内部完全没有使用证据。
- consolidated 失败没有被直接解释为事实丢失：规则仍保留正确事实，部分下降来自时间措辞和输出格式。
- 本阶段没有训练 utility model，也没有实现 utility-aware retention；这些属于 v0.2。

## Stage 4 日志：多模态检索轻量案例

### 原计划

理解 OCR-first RAG 的表示损失，使用少量论文页面比较视觉页面检索、原生 PDF 文本检索和 OCR 文本检索，并判断多模态记忆是否应立即进入主线。

### 实际完成

- 使用 8 个页面、5 个手工查询建立视觉、原生文本和 OCR 文本三路对照。
- 视觉路径使用 VisRAG-Ret；两条文本路径使用 MiniCPM-Embedding。
- 文本按固定 token 窗口切块，页面得分取最高块相似度；OCR 使用固定 Tesseract 参数且不做人工修正。
- 保存查询—页面的全部 120 个分数、top-3、文本块、输入 hash、配置和验证记录。
- 将正式模态命名统一为 `visual`、`native_text` 和 `ocr_text`。

### 验证结果

- 指定页排第一的次数为：visual `5/5`、native text `4/5`、OCR text `3/5`。
- 120 个页面分数均被重新计算并通过校验；两种文本路径均达到 100% tokenizer 覆盖。
- 结果只说明这 8 页、5 问下表示形式改变了检索行为，不构成一般性的视觉优越性结论。

### 与原计划的偏差

- 实际结果比原计划的定性 demo 多了完整分数重算和结构化验证，但仍不是统计性 benchmark。
- 不同路径使用不同 encoder，无法把差异完全归因于模态。
- 未运行多模态生成器，也没有证明多模态长期记忆能够改善最终回答。
- 最终判断仍是“作为后续扩展”：v0.2 主线先聚焦 utility-aware retention。

## v0.1 最终结论

v0.1 最重要的产出不是“四个项目复现成功”，而是一条有系统、有实验且有边界说明的研究路径：

1. 持久化与恢复可以作为后续记忆实验的可靠工程基底。
2. 在本实验范围内，全量检索在 10,000 条记忆时仍保持较高 Recall@5，但固定预算下的保留策略显著影响目标事实可达性。
3. 检索 Recall 不能替代回答效用指标；即使目标证据出现在 top-k 中，生成仍可能失败。
4. 记忆整合的措辞和输出协议也会改变测得效用，不能只检查事实是否“还在”。
5. 多模态表示值得保留为扩展方向，但当前证据不足以让它取代 retention 主线。

因此 v0.2 聚焦一个更窄的假设：

> 在固定 memory/token budget 下，utility-aware retention 能否比 recency、importance 和 semantic deduplication 保留更多下游任务性能？

## v0.1 未解决的问题

- 没有第二台干净主机的安装复验。
- 数据主要是英文合成模板，缺少新的 blind real-world test set。
- 生成记忆默认隔离、session/user 隔离和长期吞吐尚未实现。
- 没有训练或评估 utility-aware retention policy。
- 多模态实验规模小，且没有最终答案生成评估。

这些项目是后续工作的输入，而不是 v0.1 发布的阻塞项。
