## 发现 1 — [P1] 共享命名扩展阻断了 E1 的公开审计入口

位置：[verify_run.py](../experiments/utility-retention/audits/verify_run.py#L24)、[experiment_contracts.py](../src/longmem/experiment_contracts.py#L8)。

E1 将共享 contracts 纳入源码身份；后续新增 retrieval_frequency、hindsight_loo、best_subset 后，E1 扩展 audit 仍要求当前所有源码逐字节等于原始版本。本轮按其入口直接复现：

```text
ValueError: Current analysis source differs from run: src/longmem/experiment_contracts.py
```

E1 冻结压力集、扩展主运行和扩展诊断均有该文件不一致；两个 pilot 还存在 runner.py 变化。E2–E4 当前记录的源码身份则匹配。

影响：从最终 v0.2 checkout 无法直接按现有命令验证前置 E1。当前 README 虽提示恢复归档环境，却没有提供完整可执行恢复入口；共享名称的无行为变更也会使旧审计不可用。

建议：保留原 manifest 和归档源码，通过独立兼容审计入口或可执行归档环境复验。长期区分“当前代码续跑身份”与“归档结果审计身份”，不能为了通过而改写旧 hash 或简单关闭校验。新增一个最终 checkout 能验证 E1 归档产物的检查。

## 发现 2 — [P2] E1 强审计绕过公共模型配置，绑定本机目录布局

位置：[verify_run.py](../experiments/utility-retention/audits/verify_run.py#L44)。

该脚本从公共 manifest 的模型 basename 推导仓库外 `local-assets/models/<name>`，直接加载 tokenizer，没有 --model-config，也不走 load_config / LONGMEM_CONFIG。解决发现 1 后，按 README 将模型放在其他合法路径的用户仍可能无法运行审计。

建议：在新审计入口使用公共配置定位模型，并比对归档模型身份；不从公开 basename 猜磁盘布局。无需为此重跑已完成的生成实验。

## 发现 3 — [P2] 规范后端名与公共实现不一致，v0.2 继续依赖旧拼写

位置：[开发指南](experiment-development-guide.md#L121)、[config.py](../src/longmem/config.py#L35)、[generation.py](../src/longmem/generation.py#L25)、[runner.py](../experiments/utility-retention/utility_retention/runner.py#L62)。

中英文指南推荐 hash_test / evidence_test，并将连字符形式描述为兼容输入；实际公共实现只接受 hash-test / evidence-test。本轮调用两个推荐名称均得到 Unknown backend 的 ValueError。v0.2 为复用旧后端，仍在新 runner 写入连字符形式。

这是 v0.1 已存在的文档—接口问题，v0.2 继续承接，不应归咎于本轮新增算法。

建议：在公共配置边界增加明确的 alias 归一化，保留旧输入，稳定一种新输出；覆盖两种输入的等价性。结合发现 1 的归档方案处理源码身份，避免一次拼写修复使全部冻结审计失效。

## 发现 4 — [P2] 公共 contracts 尚不能描述 v0.2 实际结果

位置：[experiment_contracts.py](../src/longmem/experiment_contracts.py#L8)、[e2_metrics.py](../experiments/utility-retention/utility_retention/e2_metrics.py#L30)、[e4_analysis.py](../experiments/utility-retention/utility_retention/e4_analysis.py#L11)。

实际产物新增 prediction.* 和 diagnostic.* 等指标，metric_key 仍只接受 retention/retrieval/answer/cost；本轮 metric_key('prediction', 'mae') 直接失败。E4 的 predicted_sum_optimal / hindsight_loo_sum_optimal 是局部候选，不在公共策略集合中；oracle_utility 虽在中文指南中被标为只读兼容名，代码集合仍不区分新写与旧读。

此外，E1 的 condition 是存储/上下文干预，v0.1 MEMORY_CONDITIONS 是内容条件。这些在当前局部 key 下没有发生混算，但不能交给同一个 canonical_condition 处理。所有主 manifest 使用 longmem-experiment-v1，却缺少独立的 payload 契约来说明不同 artifact 的字段。

建议：定义策略族、模型候选、内容条件、存储干预和上下文干预的不同字段/命名集合，增加 artifact_type 与 payload schema 映射；旧格式通过只读 adapter 读取。schema 的 v1 不必机械改成 v2——实验版本与数据格式版本应分开——但必须说明它只约束什么。不要将所有局部 condition 直接塞进 MEMORY_CONDITIONS。

## 发现 5 — [P2] 同名 baseline 的跨版本语义发生变化，缺少统一映射

位置：[v0.1 benchmark](../experiments/memory-budget/benchmark.py#L136)、[v0.1 数据生成](../experiments/memory-budget/generate_dataset.py#L27)、[v0.2 baselines](../experiments/utility-retention/utility_retention/baselines.py#L38)。

| 名称 | v0.1 | v0.2 |
|---|---|---|
| importance | 随机合成元数据排序 | 固定 prompt 的模型 1–5 评分，非法输出回退 3 |
| semantic_dedup | 代表项优先，随后包含被排除项，以条数预算截取 | 仅在代表项中按新旧填 token budget，不回填重复项 |
| budget ratio | 相对 memory 条数 | 相对序列化 token 总数 |
| retrieval | Memory-budget 路径使用 FAISS 索引 | Engine 对隔离列表直接计算 embedding 相似度排序 |

这些改变各自可成立，现有阶段日志也说明了部分差异；问题是没有一份公共机器可读映射，跨版本合并报告时仅按策略名或 budget_ratio 分组会产生错误可比性。

建议：保留稳定 policy family，同时增加 implementation/variant、budget_unit、dedup_backfill 和评分来源等描述。发布总报告显式说明跨版本不能直接当同一 baseline 的效果变化。v0.2 复用了 embedding/generation backend，但没有复用持久化 store/FAISS 检索路径，不宜描述为完整复用 v0.1 在线系统。

## 发现 6 — [P2] 答案评分重复实现，缺少跨版本一致性约束

位置：[v0.1 score.py](../experiments/memory-utility/score.py#L7)、[v0.2 engine.py](../experiments/utility-retention/utility_retention/engine.py#L15)。

两处独立实现同样的 casefold、标点删除、冠词删除、EM 和 token F1，只是返回字段不同。v0.2 内部各阶段复用 Engine.score 是正确的，但跨大版本评分还不是单一实现。未来只修改一边可能让同名 answer.exact_match / token_f1 的语义漂移；当前没有证据表明数值已发生差异。

建议：新版本建立公共评分模块和旧字段 adapter，保留冻结实现用于历史审计；增加版本间评分一致性用例。不要强行共用 prompt：v0.1 系统 demo 的引用要求与 v0.2 短答案实验协议不同，保留明确版本是合理的。

## 发现 7 — [P2] 发布入口状态与双语指南未收敛，CI 未覆盖新增实验源码

位置：[实验 README](../experiments/utility-retention/README.md#L1)、[英文开发指南](experiment-development-guide.en.md#L44)、[CI](../.github/workflows/test.yml#L20)、[pyproject.toml](../pyproject.toml#L7)。

- 实验 README 标题仍是 Stage 1 & Stage 2，开头说 Stage 3/4 尚未实施，后半部分又说全部 COMPLETE。开发步骤段落的历史描述没有统一标记为历史。
- 顶层 README 仍把 v0.2 描述为未来假设，缺少新版研究结果入口；中文指南新增三种策略，英文指南未同步。
- pyproject 和 CITATION 仍为 0.1.0，这在开发期间合理，但正式 v0.2 发布前需一起更新，而不是只改文档标题。
- CI Ruff 只扫描 src/tests/scripts/integrations，不扫描 v0.2 的实验实现。当前人工检查通过，之后提交却不会自动守住这一质量边界。

建议：建立当前版本总入口与阶段完成表，保留历史日志但明确时态；补齐双语契约和 v0.2 release checklist。CI 定向加入活跃 v0.2 源码并排除归档 source-snapshot，不以自动格式化冻结源码的方式处理全仓历史告警。

## 复用中已做对的部分

- 配置、JSON/JSONL I/O、原子写入、hash、runtime metadata、embedding 和 generation backend 均有实际公共模块复用。
- E2–E4 复用同一 Engine、historical_features、selector、predict、响应 key 与评分/汇总函数；未发现每阶段另写一套核心生成器。
- E4 的 hindsight_loo、hindsight_loo_sum_optimal、best_subset 区分正确，full-a10 与 full 没有在正式策略表中混淆。
- E3/E4 对复用的 paired 函数覆盖了旧 validation 描述，未发现正式结果仍被错误标成验证集的现象。
- 阶段独立 prepare/run/audit 生命周期是合理的冻结边界，不应只为减少文件数而合并。优先抽取稳定评分与契约，保留实验特有编排。

## 建议的修复顺序与复验范围

1. 先建立不修改旧结果的归档审计路径，解决发现 1、2。
2. 建立新输出契约与跨版本 baseline 映射，再处理后端 alias 和评分复用，避免反复打破 frozen hash。
3. 更新总 README、实验 README、双语指南、版本元数据和 CI 范围。
4. 明确发布输入清单。现有 E3/E4 测试会读取 results 中的冻结 predictor/strategies/E1 dataset manifest；不能照搬 v0.1 的忽略原始结果规则后误删这些必要输入。大型原始结果可单独归档，但要给可执行获取与校验路径。
5. 在干净 checkout 上运行 CPU 测试、活跃代码 Ruff、E1 归档审计及 E2–E4 结果重算。仅当评分、检索、选择或 prompt 的实际行为改变时，才安排新版本模型运行。

没有发现需要立即重跑全部四阶段模型实验的证据；本轮最优先的是恢复复验入口与完成发布契约，而非扩大实验。
